# AI Survey Pulse

Инструмент для повторяющегося цикла: **опрос → анализ → портреты + дашборд → реакция**.
Опросная платформа (`AiEmployeeTest`) хранит данные в Google-таблице. Мы периодически
запускаем волны опроса по мере внедрения ИИ и следим за динамикой показателей.

Детерминированная часть (скачать, распарсить, посчитать, сверстать PDF) — в `tools/`,
выполняется кодом. Творческая часть (прочитать разбор и написать тёплые портреты) — за моделью.

## Что делают инструменты (`tools/`)

- `survey_lib.py` — общая библиотека: `fetch_sheet`, `parse`, декодирование ответов, скоринг знаний.
- `analyze.py` — качает/парсит таблицу → `analysis.json` (машине) + `analysis.txt` (модели: агрегаты + разбор по каждому). Поддерживает `--prev` для сравнения волн.
- `render_portraits.py` — из `portraits.json` (текст пишет модель) верстает по одному A4-PDF на человека (бренд-стиль опроса, зелёный `#005C32`). Chrome/Edge находит сам. **Падает с кодом 2, если портрет не влез на один лист** — это не придирка, портрет уходит человеку как открытка.
- `make_dashboard.py` — собирает `dashboard.html` из `analysis.json` (все цифры) + `story.json` (тексты пишет модель). Цифры руками не переписывать: так дашборд расходится с данными.
- `metrics_column.py` — считает столбец для **второй таблицы** (метрики отдела), сверяет с уже записанным, показывает просроченные мероприятия и проверяет антиметрики.
- `config.json` — ID таблицы, карты декодирования ответов, пороги портрета, **словарь смягчения формулировок**.
  Правильные ответы блока знаний берутся из листа `Answers` («Номер правильного ответа»);
  `knowledge_correct` в конфиге остаётся только запасным вариантом.

`reference/` — `metrics.md` (что значат метрики и как реагировать), `framing.md` (правила мягких формулировок), `dashboard_example.html` (эталон дашборда — копировать и переписывать под волну).

## Рабочий процесс

1. **Анализ.** Скачать и разобрать текущую волну — одной командой:
   ```
   python tools/analyze.py --out <РАБ_ПАПКА> --fetch            # или --xlsx FILE
   ```
   Сравнение с прошлой волной **происходит само**: каждая волна сохраняется в историю
   (`config.json` → `history_dir`), а следующий запуск автоматически берёт последнюю
   более раннюю волну для сравнения. Ничего не нужно помнить и передавать вручную.
   (`--prev FILE` — принудительно указать волну; `--no-history` — не читать/не писать историю.)

   Прочитать `analysis.txt`. Это основа для всего. Первым делом — озвучить пользователю
   общую картину и (со второй волны) изменения `wave_diff`; при снижении любой из трёх опор
   на ≥5 пунктов `analysis.txt` сам выведет «ВНИМАНИЕ: снижение…» — назвать и предложить разобраться.

   Если в отчёте есть блок **НАБОРЫ ВОПРОСОВ** — вопросы раздавались персонально
   (см. ниже). Тогда обязательно сказать пользователю, сколько вариантов набора было
   и какие доли от чего считались; молча приводить проценты как «по отделу» нельзя.

2. **Портреты.** По каждому прошедшему сотруднику (кроме тестового профиля — исключается автоматически)
   написать тёплый портрет по правилам ниже. Сложить в `portraits.json` (список объектов
   с полями `id,name,role,dept,lead,anchor,scenarios,learning,natural,focus`), затем:
   ```
   python tools/render_portraits.py --portraits portraits.json --out <РАБ_ПАПКА>
   ```
   Получатся `pdf/NN_Фамилия.pdf` — по одному листу А4, для отправки в личку как благодарность.

3. **Дашборд.** Собрать генератором — цифры подставятся сами:
   ```
   python tools/make_dashboard.py --analysis <РАБ_ПАПКА>/analysis.json --story-template story.json
   # заполнить story.json (заголовки, выводы, рекомендации, по две строки на человека)
   python tools/make_dashboard.py --analysis <РАБ_ПАПКА>/analysis.json --story story.json --out <РАБ_ПАПКА>/dashboard.html
   ```
   Модель пишет только смысл: `findings`, `recommendations`, `short`/`focus` в таблице людей.
   Средние, доли, распределение портретов, знания, калибровка, вовлечённость, Δ к прошлой волне —
   считаются из `analysis.json`. `reference/dashboard_example.html` остаётся образцом тона.

4. **Метрики отдела.** Посчитать столбец для второй таблицы:
   ```
   python tools/metrics_column.py --analysis <РАБ_ПАПКА>/analysis.json --date ДД.ММ.ГГГГ
   ```
   Показывает, что вставить, что там было записано раньше и где расхождение; плюс
   просроченные мероприятия и сработавшие антиметрики.

5. **Реакция.** На основе `metrics.md` предложить конкретные шаги: форматы обучения под запрос
   большинства, кого звать в амбассадоры, где просела метрика и что с этим делать.

## Вторая таблица — метрики, антиметрики, мероприятия

`config.json → metrics_sheet_id`, лист отдела — `metrics_dept_sheet` (по умолчанию `БА`).
Скилл **читает** её анонимно по export-ссылке и **не пишет**: для записи нужен OAuth или
сервисный аккаунт, которых у скилла нет. Поэтому `metrics_column.py` печатает готовые
значения (и по желанию CSV) — вставляет их человек.

**Как считается каждая строка — утверждено владельцем 15.09.2026**, полная таблица
в `reference/metrics.md` → «Таблица метрик отдела». Свои определения не изобретать:
если строку по утверждённому правилу посчитать нечем, значение пустое и причина названа.

Три правила, на которых обжигались:
- **Доли — от численности отдела** (лист `Usages`, «Участвует? ≠ Нет»; сверяется с
  «Количество сотрудников в отделе» в таблице), а не от прошедших волну. Цель-численность
  больше отдела `metrics_column.py` называет вслух.
- **Вопроса не было в волне — пусто, а не 0.** Волна знаний (601–615) не даёт ни 511,
  ни портретов: регулярность пустая, энтузиасты берут портрет из последней волны с портретами.
- **В ai-tools — только папка отдела** (`config.json → ai_tools_folder`), единица —
  инструмент, а не файл; автор — колонка «Автор / поддерживает» в `index.md`, а не коммиты:
  чужие материалы заливают пакетом. Считает `ba_repo.py` по клону `ai_tools_repo`
  (перед подсчётом делает `git fetch`; `--repo-asof ДД.ММ.ГГГГ` — на дату).

Антиметрики «Ложная уверенность» (рост калибровки ≥22 п.п.), «Зависимость от ИИ»
(падение знаний к прошлой волне — ранний срез той же волны прошлой не считается) и
«Репозиторий-витрина» (авторов из отдела ≤ 2) проверяются автоматически.
«Снижение качества задач» — вне данных скилла.

**Приватность.** Портреты содержат имена и психологический разбор реальных людей — это внутренний
материал. Складывать вне git-репозитория проекта (например `C:\Scripts\_AI_Survey_Portraits\`),
не коммитить, не публиковать. Рассылка каждому в личку — действие пользователя (не отправлять от его имени без явного согласия).

## Как писать портрет (правила — соблюдать строго)

Цель портрета — поблагодарить и мягко сориентировать человека во внедрении ИИ. **Никого не обидеть.**

Жёсткие запреты:
- НЕ называть баллы, проценты, число правильных ответов, ярлык портрета («Оппонент» и т.п.).
- НЕ сравнивать с коллегами и с «средним по отделу».
- НЕ формулировать требования, не указывать на недостатки в лоб, без клише и менторства.

Обязательные переформулировки (полный словарь — `reference/framing.md`):
- пробел в знаниях → **точка роста** / «фундамент, который стоит укрепить»;
- мотивация/заинтересованность → **активное участие**, вовлечённость, живой отклик;
- «не пользуется ИИ» → «в начале пути»; «не заинтересован» → «пока присматривается».

Четыре смысловых блока портрета (тёплый, конкретный, человеческий тон):
- `lead` — 2–3 фразы: точный, узнаваемый образ человека и его сильная манера.
- `anchor` — короткая строка сильных сторон («На что приятно опереться: …»).
- `scenarios` — **какие сценарии ИИ ему ближе** (из ответов: тема 203, характер задач).
- `learning` — **какой формат обучения ему полезнее** (204: воркшопы / самостоятельно / гибко; глубина 209; мероприятия 210).
- `natural` — **как сделать ИИ естественной потребностью, а не обязанностью** (привязать к его реальным задачам/мотивам).
- `focus` — **на что мягко обратить внимание** (точка роста, поданная как возможность и опора на его же сильную сторону).

Каждый блок должен опираться на конкретные ответы этого человека (см. его секцию в `analysis.txt`),
а не на общие слова. Портрет обязан помещаться на один лист А4 (примерно 380–450 слов суммарно).

## Волна знаний: портрет по приросту, а не по характеристикам

Бывает волна, где все вопросы оцениваемые: она меряет усвоение материала после обучений,
а не отношение к ИИ. Так устроена вторая волна (`601–615`: ИИ-модели, платные и бесплатные
способы, безопасность). Вопросов, которые питают принятие, интерес и безопасность,
в такой волне нет, поэтому **три характеристики, «Средний балл» и ярлык портрета остаются
пустыми — это норма, а не сбой данных**. Ругаться на «нет портрета» в такой волне не нужно.

Опора для портрета здесь другая:

- **прирост**: `Прошлая волна: X% -> сейчас Y%` в секции человека `analysis.txt`.
  Проценты, а не число правильных: наборы вопросов у волн разные;
- **по отделу**: строка `Знания по людям: выросли … просели … без изменений …`;
- **по блокам**: какой из трёх блоков просел у человека — там обучение не легло;
- **калибровка**: самооценка из прошлой волны против факта в этой;
- **таймауты**: `TIMEOUT` — это нехватка времени, а не незнание, и в портрете
  их нельзя подавать как пробел.

Правила текста те же: ни процентов, ни сравнения с коллегами, ни ярлыков. Рост показывается
словами («материал лёг», «стало заметно увереннее»), просадка — как точка роста с опорой на
сильную сторону. Человеку, у которого нет прошлой волны, про динамику не писать вообще:
у него это первая точка, и сравнивать не с чем.

## Персональные наборы вопросов (колонка «Ограничение (по ID пользователя)»)

На листе `Questions` четвёртая колонка задаёт, **кому показывается вопрос**. Пусто = всем.
Так можно давать разным респондентам разные наборы, укорачивать опрос одним и удлинять другим.

| В ячейке | Кому вопрос |
|---|---|
| *(пусто)* | всем |
| `2,5,7` | только ID 2, 5, 7 |
| `2-8` | ID с 2 по 8 |
| `!5` или `-5` | всем, кроме 5 |
| `кроме 5, 7` | всем, кроме 5 и 7 (`кроме` действует до конца строки) |
| `2-8, !5` | 2,3,4,6,7,8 |
| `все` / `никому` | явно всем / никому (вопрос де-факто выключен) |

Разбирается функцией `parse_restriction` в `survey_lib.py`; **тот же синтаксис** реализован
в `Code.gs` бэкенда — менять только синхронно, иначе статистика посчитает не тот набор,
который человек видел. Непонятный токен не гадается: он попадает в `restriction_errors`
(и в консоль `analyze.py`), а бэкенд на нём падает с явной ошибкой.

Что из этого следует для анализа — `analyze.py` уже учитывает, но проговаривать вслух:
- **Доли считаются от тех, кому вопрос задавался**, а не от всех прошедших. В отчёте у таких
  метрик указано «вопрос задавали N чел.».
- **Знания — от личного набора** человека: `7/8` и `7/10` это разные вещи. Для сравнения
  людей и волн использовать процент (`knowledge_pct`), а не «баллы из N».
- В разборе по человеку «не задавался» ≠ «пропустил». Первое — решение админа, второе — его выбор.
  В портрете **нельзя** трактовать незаданный вопрос как отсутствие интереса.
- Если набор укоротили ниже минимума (`adoption` 6, `interest` 6, `safety` 4 ответа —
  `js/config.js → portrait.dimensions.minAnswers`), характеристика **не считается**,
  портрет выходит пустым. `analysis.txt` предупредит об этом отдельной строкой,
  а перед запуском волны это же покажет `auditQuestionSets()` в Apps Script.
- Сравнение волн с разным составом вопросов помечается в `wave_diff.questions`
  (`added` / `removed`) — при разном составе средние по знаниям сравнивать только в процентах.

Резать без последствий для баллов можно: 204, 206, любые знаниевые (301–310), 511 (уйдёт
самооценка), а также до 2 вопросов принятия, до 2 интереса и 1 безопасности.

Сам минимум живёт на листе `Settings` в строке `min_answers` (значение-JSON) — один источник
для фронтенда, бэкенда и статистики. `config.json → portrait_min_answers` только запасной.

## Волны

Номер текущей волны лежит в `Settings ▸ wave`, и он же пишется в колонку **«Волна»** листа
`Results`. Ответы разных волн не смешиваются: бэкенд читает и обновляет только строки текущей
волны, новые ложатся ниже. Итоги волны перед перезапуском уезжают в лист `Employees_history`
(это делает `startNewWave()` в Apps Script).

Что из этого следует для разбора:

```
python tools/analyze.py --out DIR --fetch --list-waves   # какие волны есть в таблице
python tools/analyze.py --out DIR --fetch                # текущая волна (Settings ▸ wave)
python tools/analyze.py --out DIR --fetch --wave 1       # прошлая волна из архива
```

- Прошлая волна разбирается полноценно, если её итоги есть в `Employees_history`; отчёт тогда
  пишет «Баллы и портреты взяты из архива». Если архива нет, баллы возьмутся из текущего
  `Employees` — то есть будут от последней волны, и `analyze.py` скажет об этом прямо.
  Молча выдавать такие цифры за прошлую волну нельзя.
- Снимок каждой волны кладётся в `history_dir` под именем `wave_<дата>_w<N>_<n>p.json`.
  Предыдущая волна для сравнения выбирается по номеру, при равных — по дате; файлы старого
  формата (без номера) читаются по дате, так что накопленная история не теряется.
- Если колонки «Волна» в `Results` нет, `analyze.py` предупредит: ответы новой волны
  перезапишут прошлые. Лечится однократным `setupWaveColumn()` в Apps Script.

Порядок перезапуска волны (в таблице): `analyze.py` на текущей волне → `previewNewWave()` →
`startNewWave()` → переключить галки «Включен» у вопросов → `validateSurvey()` → рассылка.

сохраняются (`analysis.json`, срез в `history_dir`, разбор по людям, флаг `lead: true`),

Вне отдела (`Участвует? = Нет`) — тоже не считаются.

## Свободные ответы и пустые опоры (02.11.2026)

Приложение не оценивает «свой вариант» (`js/survey.js`), а характеристика считается только при минимуме ответов с весом (лист `Settings`, `min_answers`). Поэтому у человека с несколькими свободными ответами принятие или интерес могут остаться пустыми, а с ними и портрет. `analyze.py` теперь пишет в разбор строку «НЕТ ОЦЕНКИ: … ответов с весом N из M, свои ответы: …». Досчитать можно файлом `own_answers_map.json` (`config.json → own_answers_map`, вне набора, содержит ПДн): по волне и ID — какому варианту ближе свободный ответ и почему. Оценка помечается «по разбору свободных ответов», в таблицу опроса не пишется, соответствия подтверждает человек. Веса — `tools/portrait_weights.json`, обновляются `python tools/own_answers.py --sync` из `js/config.js` приложения (нужен node).

**Как работать со свободными ответами (агент делает сам, человек подтверждает):**
1. `analyze.py` показал «НЕТ ОЦЕНКИ …» — прочитать свободные ответы человека (`analysis.txt`, секция человека).
2. Каждый свободный ответ на вопрос с весом отнести к ближайшему варианту или оставить без оценки («не по теме», «не было примеров»), записать в `own_answers_map.json` с причиной, `confirmed: false`; показать человеку таблицей «вопрос — свой ответ — вариант — почему».
3. После «да» — `confirmed: true`, повторить `analyze.py`, затем `python tools/own_answers.py --gs analysis.json` и вставить полученный `MANUAL_SCORES` в `backend/Code.gs`.
4. Таблицу опроса агент напрямую не пишет, если нет коннектора: запись делает функция `applyManualScores()` (сначала `previewManualScores()`), которую человек запускает в Apps Script. Править ячейки руками через браузер — крайний случай: вводить значения по одному (Tab в `type` уходит в ячейку пробелом).

Строка «Субъективная экономия времени» считается долей рабочей недели (`work_week_hours`, 40), как в таблице метрик.
Темы голосования привязываются к встречам из таблицы метрик (`story.json → vote_map` для тем с другим названием встречи).

## Калибровка, таймауты, вовлечённость

Три вещи, которые `analysis.txt` выводит отдельными разделами — их легко проглядеть.

**Калибровка** = «Балл самооценки» − «% верных в блоке знаний». Плюс — человек оценивает себя
выше факта, минус — ниже. Это антиметрика «ложная уверенность» из листа `Metrics`; порог ±20 п.п.
(`config.json → calibration_gap`), тревога — рост среднего разрыва на ≥22 п.п. между волнами.
В портрете **нельзя** писать про разрыв прямо. Переоценка — повод дать разбор ошибок на реальных
кейсах (а не новый инструмент); недооценка — повод вернуть человеку уверенность, подав его
сильную сторону как сильную (пример: «сильные навыки при скромной самооценке»).

**Не успел ≠ не знал.** Фронтенд пишет в `Results` маркер `TIMEOUT`, когда истёк таймер
знаниевого блока. Для метрики знаний это по-прежнему неверный ответ, но в разборе видно причину.
Пустая ячейка без маркера — ответы, записанные до внедрения маркера: по ним различить нельзя,
так и говорить.

**Вовлечённость** берётся с листа `Usages` по колонке `ID` (не по ФИО). «Вовлечён» — хотя бы один
признак «Да»: агент, ai-tools, артефакт, мероприятия, использование инструмента. Если покрытие
меньше числа прошедших — часть людей просто нет на листе, это надо называть, а не молчать.
